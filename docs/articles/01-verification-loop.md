# The night our agent invented a phone number — building a self-correcting agent team with Strands Graph

*Draft for builder.aws — article 1 of 3 for the Agents for Humans Hackathon (Sonae project)*

On its very first live run, our disaster-preparedness agent did something quietly terrifying: it
invented a phone number.

The Planner agent was drafting an evacuation timeline for a 78-year-old woman living beside the
Chikuma River. Step 4 read: *"If she cannot walk, call 長野市災害対策本部 at 026-224-5011."* The
number looks real. It has the right city prefix. It is plausible in exactly the way that makes
large language models dangerous in safety-critical domains — and it appears in none of the
official data our agents are allowed to use.

It never reached a user. This post is about the architecture that caught it: a self-correcting
verification loop built with the Strands Agents SDK's `Graph`, and the prompt-engineering lessons
from making that loop actually converge.

## The shape of the problem

Sonae builds family evacuation plans from Japanese government open data (hazard-map rasters, the
national evacuation-site registry, JMA feeds), then watches official alert feeds and runs the plan
when signals fire. Everything user-facing is generated by an LLM; everything user-facing can kill
someone if it's wrong. "Be careful" is not an architecture. We needed a structural guarantee that
no factual claim ships unaudited.

## A graph with an adversarial edge

Strands' `GraphBuilder` lets you wire agents into a DAG — and, crucially, lets an edge carry a
condition and lets nodes re-run when revisited:

```python
builder = GraphBuilder()
builder.add_node(make_cartographer(), "cartographer")   # reads hazard maps & shelter registry
builder.add_node(make_planner(), "planner")             # drafts the family timeline
builder.add_node(make_verifier(), "verifier")           # audits every claim
builder.add_edge("cartographer", "planner")
builder.add_edge("planner", "verifier")
builder.add_edge("verifier", "planner", condition=_needs_revision)   # the interesting edge
builder.set_entry_point("cartographer")
builder.reset_on_revisit(True)
builder.set_max_node_executions(8)
```

`_needs_revision` parses the Verifier's structured output; if `approved` is false, the graph routes
back to the Planner — whose input now contains the rejection and its `revision_request`. When the
Verifier approves, its outbound edge condition is false, no node becomes ready, and the graph
terminates naturally. Convergence or the execution cap, whichever comes first — and our runner
refuses to persist any plan whose final verification report isn't an approval.

Two design choices did the heavy lifting:

**The Verifier holds the same tools as the Cartographer.** It doesn't take the draft's word for
anything: it re-geocodes, re-samples the hazard tiles, re-queries the shelter registry, and quotes
the evidence for every claim it accepts. Independent re-derivation, not proofreading.

**Inter-agent messages are typed.** Each agent's system prompt embeds the JSON Schema of its
required output (generated from Pydantic models), and every hop is validated. A hallucinated field
name is a loud failure, not a silent propagation.

## What actually happened on run #1

The Verifier caught the phone number — `verdict: unsupported`, exactly as designed. Then the loop
failed to converge anyway, and the failure mode is worth sharing because every verifier-pattern
team will hit it:

1. **The Verifier nitpicked a correct claim.** The Planner had written that a river flood warning
   (氾濫警戒情報) maps to alert Level 3 — which is precisely right under Japan's Cabinet Office
   framework. The Verifier, having no authority to consult, asked for it to be "double-checked."
   Unfalsifiable requests can't be mechanically applied, so the loop spun.
2. **Vague revision requests produce vague revisions.** "Verify semantic alignment" is not an
   edit; "delete the phone number in step L4" is.

The fixes were prompt-architectural, not code:

- **Give the Verifier its ground truth.** We embedded the official alert-level equivalence table
  in the Verifier's prompt and instructed: claims consistent with the table are supported *by
  definition*. A verifier without an authority list will invent doubt.
- **Constrain rejections to three categories:** contradicted by evidence, misaligned with the
  table, or a safety-critical specific (number, name, contact) absent from evidence. Style is the
  drafter's business.
- **Force mechanical revision requests.** The rejection must be an instruction the drafter can
  apply without judgment.
- **Remove the temptation at the source.** The Planner's prompt now forbids inventing contact
  details outright — the best verification finding is the one that never occurs.

Run #2 converged in a single pass: 16 claims checked, each with a verbatim evidence quote, zero
revision loops. The plan it approved moved the grandmother's departure hours earlier than the
official evacuation order that night in 2019 would have — but that counterfactual is another
article.

## The asymmetric failure rule

One more structural decision matters in this domain. In the watch pipeline (Sentinel → Messenger →
Verifier), a rejected notification gets one revision pass. If verification still fails during a
Level 3+ event, Sonae does **not** send the AI's prose — and does **not** stay silent either: it
relays the official bulletin text verbatim, with citations. AI prose fails closed; the official
signal fails open. In disaster communication, silence is the one unacceptable failure mode.

## Takeaways

- A verifier agent is only as good as its stated authority. Enumerate what it must accept, or it
  will manufacture uncertainty.
- Make rejections mechanical and revisions verbatim-applicable, or your loop oscillates.
- Type every inter-agent hop; schema validation catches what prompts can't.
- Decide per output class whether it fails open or closed — before the night it matters.
